# 英超竞猜榜单项目设计说明

## 当前已确认

### 第一里程碑范围

- 当前实施批次以“数据链路优先”为原则，先打通 `premierleague.com` 数据获取、规范化和落盘链路。
- 第一里程碑只覆盖官网积分榜抓取、内部模型规范化、原始快照保存和规范化结果输出。
- 第一里程碑暂不实现计分引擎、静态页面和 GitHub Actions 发布，但目录结构和接口命名需为后续阶段预留扩展点。
- 第一里程碑优先寻找并使用官网页面背后的 JSON 数据入口，不直接以 HTML 解析作为默认方案。
- 第一里程碑以 `standings + metadata` 为最小闭环，不依赖赛程明细接口。
- 若 JSON 数据入口不可用、字段缺失或结构漂移，本轮任务应失败并保留日志，不生成推测性结果。

### 目标

- 项目用于根据玩家竞猜和英超赛果自动计算积分榜。
- 输出为可部署到 GitHub Pages 的静态网站。
- 更新方式采用 GitHub Actions 定时运行，并保留手动触发入口。
- 赛季进行中按当前官方积分榜计算临时分数。
- 页面首页优先展示总积分榜和每位玩家的得分明细。
- 页面标题下方展示数据更新时间和当前已更新轮次或比赛进度。

### 主方案

- 采用纯静态预计算方案。
- GitHub Actions 每 6 小时执行一次抓取赛果、计算积分、生成静态页面、发布 GitHub Pages，并保留 `workflow_dispatch` 手动触发。
- 页面本身不直接实时请求第三方数据源。
- 代码结构上预留独立数据源适配层，第一版只适配 `premierleague.com` 官方数据入口。
- 当前第一里程碑默认走 JSON 接口优先策略，不在这一轮同时建设 HTML 降级抓取。

### 整体架构

- 系统分为竞猜输入层、赛果采集层、计分计算层、静态站点生成层。
- 竞猜输入层负责读取玩家竞猜 CSV 并标准化。
- 赛果采集层负责抓取并落盘英超积分榜、赛程结果、轮次信息等快照。
- 计分计算层负责按 `docs/game_rules.txt` 输出每位玩家的分项得分、总分和排名。
- 静态站点生成层负责产出 GitHub Pages 所需页面和数据文件。

### 数据流

- 输入一：玩家竞猜 CSV。
- 输入二：`premierleague.com` 提供的积分榜。
- 中间产物：标准化球队数据、积分榜快照、玩家计分结果。
- 输出：静态 HTML、CSS、JS 与 JSON 数据文件。

### 数据模型

- 核心数据分为赛季配置、球队基线数据、玩家竞猜、官方赛果快照、计分结果五类。
- 赛季配置保存赛季标识、球队列表、上一赛季基准数据来源等基础信息。
- 球队基线数据保存标准名、别名、上赛季名次、上赛季积分、是否升班马。
- 玩家竞猜保存玩家 ID、昵称、前四预测、黑马列表、黑驴列表。
- 官方赛果快照保存积分榜、最近已更新轮次、数据更新时间、数据源标识。
- 计分结果保存玩家总分、排名、前四分项、黑马分项、黑驴分项及解释文本。

### 球队名映射

- 内部统一使用一个标准球队标识（如标准英文名）。
- 外部输入通过球队别名表转换为标准球队标识。
- 别名表需覆盖中文名、英文名、简称、官网名和 CSV 历史写法。
- 升班马上赛季基准名次规则：3 支升班马按照英冠排名顺序，分别映射为上赛季英超的第 18、19、20 名，以此基准参与黑马/黑驴规则计算。

### 数据源适配层

- 第一版适配 `premierleague.com` 官方页面背后的 JSON 数据入口。
- 适配层单独承担抓取、解析、规范化职责。
- 当前第一里程碑统一输出 standings、metadata 两类内部结构。
- 计分层与展示层不直接依赖外部数据源格式。
- 抓取层拆分为 provider、normalizer 和 pipeline 三个职责单元：
- provider 负责请求官网入口、保存原始响应和抛出抓取错误。
- normalizer 负责把外部字段转成内部统一结构并补齐元信息。
- pipeline 负责串联抓取、规范化、落盘和日志输出。
- 当前里程碑不实现 HTML 降级；若外部 JSON 入口不可用，直接失败并保留排查信息。

### 计分实现

- 计分引擎分为前四计分、黑马计分、黑驴计分三个模块，最后汇总总分。具体公式和细则严格参照 `docs/game_rules.txt`。
- 前四计分：按规则 `Ti × (1 - abs(Pi - Gi) / 20)` 计算。其中 `Ti` 为目标名次满分，`Pi` 为玩家预测球队本赛季实际积分，`Gi` 为目标名次球队本赛季实际积分。计算结果保留负分可能。
- 黑马计分：先判断是否满足较上赛季提升 3 名及以上。成功则加该球队本赛季积分；失败则扣除其（上赛季名次 - 3）位置在本赛季积分榜的对应积分。
- 黑驴计分：先判断是否满足较上赛季下降 3 名及以上。成功则加该球队上赛季积分；失败则扣除该球队本赛季积分。
- 特殊限制校验：预测上赛季前三名为黑马，或预测升班马为黑驴，均视为无效竞猜，需在计分前予以拦截处理（例如该项计0分或按特定规则处理，具体与规则一致）。
- 计分结果：除总分外，还要保留每个竞猜项的计算过程与明细解释，便于页面展示和人工核对。
- 动态计分：赛季中每次更新时，直接以当前最新积分榜作为“临时最终榜单”进行全量计算；赛季结束后直接作为最终结果，无需更改算法。

### 页面结构

- 首页顶部展示项目标题、数据更新时间、当前已更新轮次或比赛进度。
- 首页主体展示玩家总积分榜，按总分降序排列。
- 每位玩家需要有明细区块，展示前四预测、黑马、黑驴和各自得分拆解。
- 页面下方补充当前英超积分榜快照，方便对照分数变化原因。
- 第一版以清晰、稳定、适合长期维护为主，页面交互限定为首页内展开和收起玩家详情，不单独开发玩家详情页。

### GitHub Actions 更新流程

- 定时任务每 6 小时运行一次，并保留手动触发入口。
- 工作流顺序为拉取仓库、安装依赖、抓取官网数据、标准化并落盘、运行计分、生成静态页面、发布 GitHub Pages。
- 若抓取失败，工作流应失败并保留日志，不发布半成品页面。
- 若抓取成功但内容无变化，可以跳过无意义发布。
- 必须同时保留原始抓取快照和规范化结果文件，方便排查官网结构变化。
- 第一版额外生成计分结果 JSON，页面读取 JSON 渲染，降低后续改版成本。

## 补充设计

### 推荐技术栈

- 第一版使用 Python 3.9+ 负责数据抓取、标准化、计分和站点数据生成。
- 页面使用静态 HTML、CSS、少量 JavaScript 和 JSON 数据文件实现，不引入重型前端框架。
- GitHub Actions 直接运行 Python 脚本完成更新、生成和发布流程。
- Python 项目采用 `pyproject.toml` 管理依赖与命令入口。
- 第一版优先保证数据链路稳定和计分正确，页面效果以清晰可维护为主。

### 建议目录结构

- `data/` 保存玩家竞猜 CSV、球队基线数据和名称映射等静态输入。
- `docs/` 保存规则、设计文档、任务清单和验收清单。
- `src/` 保存项目代码，按 `providers`、`models`、`scoring`、`site`、`utils` 拆分。
- `artifacts/` 保存抓取快照、规范化数据、计分结果等中间产物。
- `site/` 保存最终发布到 GitHub Pages 的静态文件。
- `.github/workflows/` 保存定时更新和发布工作流。

### 配置与数据文件

- 需要 `data/seasons/2025-26.yml` 作为赛季配置，保存赛季编号、球队名单、升班马和上赛季基线数据定位信息。
- 需要 `data/team_aliases.csv` 作为球队别名映射文件，统一中文名、英文名、简称、官网名和历史写法。
- 需要 `data/baselines/2024-25_table.csv` 作为上赛季基线积分榜数据文件。
- 需要 `config/provider.yml` 作为数据源配置，控制官网抓取目标、超时、重试和失败策略。
- 需要 `config/site.yml` 作为站点元数据配置，控制页面标题、副标题和更新时间文案。

### 风险点

- `premierleague.com` 页面结构或内部接口字段变化，导致 JSON 数据入口失效或字段变化。
- 球队命名不一致，导致竞猜输入、官网数据和基线数据匹配错误。
- 规则边界处理出错，尤其是升班马、黑马失败扣分和黑驴无效竞猜等情况。
- GitHub Actions 虽然执行成功，但生成内容与抓取结果不一致，影响榜单可信度。

### 验证方式

- 当前第一里程碑先验证数据链路，确认能获取积分榜、轮次信息、数据更新时间并完成落盘。
- 当前第一里程碑以本地命令重复执行为主，确认相同输入下规范化产物结构稳定。
- 以 `docs/game_rules.txt` 中示例和真实竞猜 CSV 构造固定输入输出样例，验证计分引擎。
- 对球队映射做单独校验，确保每个竞猜项都能映射到唯一标准球队标识。
- 对抓取层做最小回归验证，至少确认能获取积分榜和轮次信息。
- 对页面生成结果做结构校验，确认总榜、玩家明细、更新时间和轮次信息都存在。
- 对 GitHub Actions 保留关键日志和中间产物，确保失败时可快速定位到抓取、解析、映射或计分阶段。

### 交付边界

- 第一版只支持英超单赛事、单赛季配置，不扩展到多联赛或跨赛事复用。
- 第一版只处理玩家类型为 `玩家` 的竞猜输入，不引入管理员后台或在线录入页面。
- 第一版的数据源以 `premierleague.com` 为唯一正式来源，不在实现阶段同时接入备用源。
- 若官网数据临时不可用，系统允许本次更新失败，但不能发布不完整或推测性结果。

### 第一版范围结论

- 第一版的成功标准是官网数据适配可跑通、计分准确、GitHub Pages 可自动更新。
- 第一版不以复杂交互和重前端效果为目标，而是优先交付稳定可复用的数据更新链路。
