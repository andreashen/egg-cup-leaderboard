# 英超竞猜榜单第一里程碑设计

## 背景

当前仓库已经明确了完整目标：抓取英超官网数据、计算竞猜积分、生成静态页面并自动发布。为了降低首轮实现风险，第一里程碑先聚焦数据链路，只解决“能稳定拿到官方数据并沉淀为内部统一结构”这一件事。

## 里程碑目标

- 打通 `premierleague.com` 数据获取流程。
- 优先使用官网页面背后的 JSON 数据入口。
- 生成可复用的 `standings` 与 `metadata` 规范化结果，作为后续计分和站点生成的唯一上游。
- 同时保存原始抓取快照，便于官网字段变化时排查问题。

## 非目标

- 本里程碑不实现竞猜计分逻辑。
- 本里程碑不实现静态页面生成。
- 本里程碑不实现 GitHub Actions 自动发布。
- 本里程碑不实现 HTML 降级抓取方案。

## 设计原则

- 单一职责：抓取、规范化、流程编排分层实现。
- 失败显式：请求失败、字段缺失、结构漂移均直接失败，不吞错。
- 原始可追溯：每次抓取都保留原始响应快照。
- 产物稳定：对外只暴露内部统一结构，不把外部字段直接传递到后续模块。

## 架构拆分

### provider

- 负责请求 `premierleague.com` 的目标 JSON 入口。
- 负责基础请求参数、超时、重试和状态码校验。
- 负责保存原始响应到 `artifacts/raw/`。
- 不承担业务字段解释和内部模型转换。

### normalizer

- 负责把官网字段映射成内部统一结构。
- 当前第一里程碑输出固定的 `standings`、`metadata` 两类结果。
- 负责补齐抓取时间、来源标识、当前已更新轮次等元信息。
- 对关键字段缺失直接抛错，避免产出半成品。

### pipeline

- 负责串联 provider 与 normalizer。
- 负责把规范化结果写入 `artifacts/normalized/`。
- 负责统一日志输出和退出状态。
- 后续计分和页面模块只依赖 pipeline 产物，不直接访问 provider。

## 输出结构

### raw

- 目录：`artifacts/raw/<season>/`
- 内容：官网原始 JSON 响应快照
- 用途：回放问题、对比字段变化、补充解析器测试样本

### normalized

- 目录：`artifacts/normalized/<season>/`
- 文件建议：
- `standings.json`
- `metadata.json`

### 字段口径

- `standings`：标准球队标识、排名、积分、胜平负、净胜球等后续计分可能用到的核心字段
- `metadata`：抓取时间、数据来源、赛季标识、当前已更新轮次

## 错误处理

- 请求超时：记录请求入口和超时信息后失败退出。
- 非 200 响应：记录状态码和响应摘要后失败退出。
- JSON 解析失败：记录原始片段位置后失败退出。
- 关键字段缺失：由 normalizer 明确指出缺失字段并失败退出。
- 结构漂移：视为解析失败，不自动降级到 HTML 抓取。

## 验证方式

- 本地运行一次抓取流程，确认 `raw` 与 `normalized` 两类产物均已生成。
- 重复运行抓取流程，确认规范化结果结构稳定。
- 抽样检查积分榜、赛程、更新时间和轮次元信息是否完整。
- 在模拟字段缺失或入口失效场景下，确认流程直接失败并保留日志。

## 后续衔接

- 计分引擎后续仅读取 `artifacts/normalized/` 产物。
- 页面生成后续仅读取计分结果与必要的积分榜快照。
- 若未来需要兼容 HTML 抓取，应新增 provider 实现，而不是侵入 normalizer 和下游模块。

## 当前结论

第一里程碑以“JSON 接口优先的 standings-only 数据链路”作为唯一完成标准。只要官网积分榜抓取、规范化和落盘可以稳定复跑，就进入下一阶段的计分与展示实现。
